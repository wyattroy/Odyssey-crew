## Findings

### 1. Setup-screen re-roll button was dead — confirmed, then FIXED (commit `fd8efcc`)

The integration checker reported this as a **BLOCKER**; re-tracing the source shows that
overstates it, and the checker contradicted itself elsewhere in its own report
("Affected Requirements: None").

What is confirmed: `index.html:586`'s `roll.onclick` calls `pick(TEMPERAMENTS)` →
`rint()` → `rnd()` → `state.rng()`, while `state` is `null` (index.html:403) until
`state = newState(opts)` at index.html:609. Clicking 🎲 before "Start the voyage" throws
`TypeError: Cannot read properties of null (reading 'rng')`.

Why it is not a blocker:

- The throw happens **inside a DOM event handler**, so the browser contains it. The page
  does not wedge — the button simply does nothing (plus a console error). It is a dead
  control, not a crash.
- It is reachable but cosmetic: the adjacent `<select>` sets the same temperament, so the
  capability is not lost.
- Initial seat temperaments use `TEMPERAMENTS[i%3]` (index.html:572) — deterministic, no
  RNG — so page load is safe. Line 586 is the **only** pre-game RNG caller.
- It is **pre-existing v1.0 code**, untouched by any v1.1 phase, and maps to no v1.1
  requirement. It cannot fail a v1.1 milestone that never claimed it.

**Fixed before the v1.1 tag** (commit `fd8efcc`) — the handler now uses `Math.random()`
directly, since no `?seed=` determinism contract exists before a seeded game starts. The
change removes zero draws from the seeded RNG stream: `parity.mjs` still reports 330
identical log entries for `seed=demo`, byte-identical to the pre-fix baseline.

Verified in Chrome against a hash-matched build of this worktree: with `state === null`,
`pick(TEMPERAMENTS)` still throws the original `TypeError` (so `pick()` was not weakened),
while the button re-rolls across all three temperaments over 40 consecutive clicks with no
error thrown.

### 2. BOARD-04's requirement text is stale — documentation, not code

BOARD-04 reads "Dare/Abide/**Give** are clickable affordances on the board." ECON-01,
added mid-milestone during discuss-phase 3, removed the Give verb entirely. The shipped
board is correct: exactly two buttons, verified both in source (`VERBS`, index.html:217)
and live (03-BROWSER-CHECK.md item 1 — "No third verb appears anywhere in the UI").

This is requirement text that outlived a design change, not an unmet requirement. It is
corrected in the archived `v1.1-REQUIREMENTS.md` rather than left to mislead future readers.

### 3. Phase 1's two open verification items were closed downstream but never reconciled

`01-VERIFICATION.md` still carries `behavior_unverified: 2` — both items asked for live
browser confirmation that a 0-human seeded run completes and that the same seed replays
identically. Both were satisfied later: `parity.mjs` (330 identical entries) and
`03-BROWSER-CHECK.md`'s real-browser unattended run to `⚖️ Final reckoning`. The phase-1
file was simply never updated. Bookkeeping debt, not a coverage gap.

### 4. Phase 2's critical review finding was resolved by obsolescence

`02-REVIEW.md` reads `status: issues_found` on CR-01 — Sirens' `Give` cells lost the
`Math.max(0, …)` floor on `state.world`. Phase 3 deleted **both** the Give verb and
`state.world`, so the defect no longer has anything to attach to (confirmed: zero
occurrences of either in current source). The review file was never marked closed.

Phase 3's own CR-01 (post-game-over logic clobbering the verdict screen) was fixed in
commit `917fb47`.
